# 原生通知规格

> Module: 116-notification
> Status: Implemented（脚手架阶段，宿主未接入 → 通知尚未触发）
> Last Updated: 2026-08-14

## 1. 模块概述

### 1.1 目的 — 为什么存在这个模块

让用户在无需时刻盯着应用窗口的情况下，收到 agent 运行状态的关键提示：任务完成、执行出错、请求审批、agent 异常。通知由 agent 宿主的运行时事件驱动，落地为操作系统原生通知。

### 1.2 解决的问题 — 解决哪些痛点

- agent 任务耗时较长，用户离开窗口后无法感知任务是否完成。
- 审批类操作需要用户确认，若用户不盯着窗口会卡住流程。
- agent 运行异常需要及时告知用户排查。

### 1.3 范围 — 包含与不包含

**包含**：
- 订阅宿主的会话事件流，在「一轮任务完成」「一轮任务出错」「请求审批」「agent 出错」时发出原生通知。
- 非关键事件（如任务被中止/阻断/超时/被打断）静默处理，不打扰用户。

**不包含**：
- question（提问）类通知——宿主上下文层无对应事件，唯一来源是 apiProxy 事件流中的 question 帧，本模块未接入（已记录，后续如需再接入）。
- 通知点击唤起窗口、通知内交互按钮——审批通知「点击唤起窗口」为已记录的后续实现项。
- 通知的持久化、历史记录、免打扰策略。

## 2. 用户故事

- 作为用户，我希望 agent 完成一轮任务时收到系统通知，以便无需盯窗口即可知晓任务结束。
- 作为用户，我希望 agent 执行出错时收到系统通知，以便及时介入。
- 作为用户，我希望 agent 请求审批（如工具调用）时收到系统通知，以便及时确认，避免流程卡住。
- 作为用户，我希望 agent 运行出现异常时收到兜底通知，以便前往应用查看详情。
- 作为用户，我不希望任务被中止/阻断/超时等非关键结束也弹通知，以免被噪音打扰。

## 3. 功能需求

### 3.1 任务完成与出错

- FR-116-001：系统 MUST 在 agent 完成一轮任务（正常完成）时发出原生通知。
- FR-116-002：系统 MUST 在 agent 一轮任务以错误结束时发出原生通知。
- FR-116-003：对于一轮任务以「中止、阻断、超时、被打断」等其它方式结束时，系统 MUST NOT 发出通知（静默处理）。

### 3.2 审批请求

- FR-116-004：系统 MUST 在 agent 请求审批时发出原生通知。
- FR-116-005：审批通知的正文 SHOULD 包含请求执行的工具名；无法获取工具名时，系统 MUST 使用通用提示文案。

### 3.3 agent 异常兜底

- FR-116-006：系统 MUST 在 agent 运行出错时发出兜底通知，提示用户前往应用查看详情。

### 3.4 触发条件与生命周期

- FR-116-007：通知订阅 MUST 依赖宿主上下文；宿主未就绪时系统 MUST NOT 注册通知订阅。
- FR-116-008：系统 SHOULD 使用统一的应用标识作为通知来源标识（平台显示通知来源时使用）。

## 4. 关键实体

| 实体 | 描述 | 关键属性 |
|---|---|---|
| 会话事件 | 宿主推送的会话运行时事件 | 事件类型、结束原因（kind）、附加数据（data） |
| 结束原因 | 一轮任务结束的归类 | 完成 / 出错 / 中止 / 阻断 / 超时 / 被打断 |
| 审批请求数据 | 审批事件携带的附加信息 | 请求 id、工具名、调用 id、原因 |
| 原生通知 | 落地到操作系统的通知 | 标题、正文 |

## 5. 验收场景

### 场景：任务完成通知

- Given 宿主已就绪，通知订阅已注册
- When 宿主发出一轮任务结束事件且结束原因为「完成」
- Then 系统发出标题为应用名、正文为「Agent 已完成本轮任务」的原生通知

### 场景：任务出错通知

- Given 宿主已就绪，通知订阅已注册
- When 宿主发出一轮任务结束事件且结束原因为「错误」
- Then 系统发出正文为「Agent 执行出错」的原生通知

### 场景：非关键结束静默

- Given 宿主已就绪，通知订阅已注册
- When 宿主发出一轮任务结束事件且结束原因为「被打断」或「超时」等非完成/错误类型
- Then 系统不发出任何通知

### 场景：审批请求通知

- Given 宿主已就绪，通知订阅已注册
- When 宿主发出审批请求事件且携带工具名
- Then 系统发出标题含「需要审批」、正文含该工具名的原生通知

### 场景：审批请求（无工具名）通知

- Given 宿主已就绪，通知订阅已注册
- When 宿主发出审批请求事件且未携带工具名
- Then 系统发出正文为通用确认提示的原生通知

### 场景：agent 异常兜底通知

- Given 宿主已就绪，通知订阅已注册
- When 宿主发出 agent 出错事件
- Then 系统发出提示用户查看应用详情的原生通知

### 场景：宿主未就绪不触发通知

- Given 宿主尚未接入（返回空，应用显示兜底页）
- When 主进程完成窗口创建
- Then 系统不注册任何通知订阅，因此不会有任何通知发出

## 6. 非功能需求

- **可靠性**：订阅回调须能区分事件类型与结束原因，避免误报/漏报。
- **性能**：通知为事件驱动、一次性开销，无轮询。
- **平台**：Windows + Linux（macOS 后续考虑）；Windows 下依赖正确的应用标识方能正常展示通知。
- **可维护性**：事件载荷当前为最小占位结构，接入真实宿主类型后替换，不应改变订阅与通知逻辑。

## 7. 假设与约束

- **假设**：宿主提供的会话事件结构为最小占位定义，接入真实 dsh 类型后替换（注释已注明）。
- **约束**：question 类通知无宿主上下文层事件源，本模块不覆盖（见 §1.3）。
- **约束**：审批通知的「点击唤起窗口」尚未实现，当前仅弹通知。
- **当前状态**：脚手架阶段宿主未接入（返回 null），因此本模块尚未被激活，通知实际不会触发——这是现状而非缺陷。

## 8. 依赖

- **上游依赖**：宿主集成模块（提供宿主上下文及其事件订阅能力）；应用启动编排（设置应用标识、在宿主就绪后注册通知订阅）。
- **下游依赖**：无（通知为终点动作，仅调用操作系统通知能力）。
