# overall-spec.md — 整体规格

> dsh-desktop 系统级功能规格（技术无关，2026-08-14）。
> 本文档描述系统「做什么、为什么」，不涉及实现细节。

## 1. 系统目的与目标用户

**目的**：为 deepseek-harness（dsh，一个 agent harness / 智能体框架）提供一等公民的桌面应用，而非「包一层浏览器指向 localhost」的粗壳。让 agent harness 像一个真正的桌面应用那样运行。

**目标用户**：使用 dsh 的开发者/用户，希望在桌面环境（Windows/Linux）中获得系统托盘、原生通知、无边框窗口等桌面体验。

## 2. 核心能力（用户故事）

- 作为用户，我希望应用启动后能**在系统托盘看到图标**，可随时从托盘唤回窗口或退出；关闭窗口后即退出并释放资源。
- 作为用户，我希望 agent 完成一轮任务或请求审批时，能收到**原生系统通知**，无需时刻盯着窗口。
- 作为用户，我希望应用拥有**无边框窗口 + 自绘标题栏**，与 dsh Web UI 视觉一体。
- 作为用户，我希望在应用内**粘贴剪贴板图片**，走 dsh 图片附件路径。
- 作为用户，我希望界面功能 100% 沿用 dsh 标准 Web UI，不做二次封装。

## 3. 功能需求（按域）

### 3.1 应用生命周期

- FR-000-001：系统 MUST 保证应用单实例运行；重复启动时聚焦已有窗口。
- FR-000-002：系统 MUST 在宿主（Host）就绪后才创建并加载主窗口。
- FR-000-003：系统 MUST 在关闭主窗口时退出整个进程并释放后端服务（关窗即退出）。
- FR-000-004：系统 MUST 支持通过托盘「退出」退出，退出时优雅释放宿主资源。

### 3.2 宿主集成

- FR-000-010：系统 MUST 在桌面进程内启动 dsh Host，并绑定一个空闲端口。
- FR-000-011：系统 MUST 让渲染进程同源加载 Host 提供的 Web 界面。
- FR-000-012：系统 MUST 复用 dsh 现有数据通道（HTTP 上行 + WebSocket 下行），不另建载体。

### 3.3 桌面能力

- FR-000-020：系统 MUST 提供系统托盘图标与菜单（显示主窗口 / 退出）。
- FR-000-021：系统 MUST 在 agent 完成一轮任务时发出原生通知。
- FR-000-022：系统 MUST 在 agent 请求审批时发出原生通知。
- FR-000-023：系统 MUST 提供无边框窗口，并支持窗口最小化/最大化/关闭控制。

### 3.4 安全

- FR-000-030：系统 MUST 隔离渲染进程（禁用 Node 集成、开启上下文隔离与沙箱）。
- FR-000-031：系统 MUST 限制渲染进程的导航范围与权限申请。

## 4. 非功能需求

- **性能**：宿主启动不应阻塞窗口创建流程之外的不必要等待；桌面壳自身开销最小化。
- **可移植性**：支持 Windows + Linux（macOS 后续）。
- **可维护性**：进程边界可迁移到子进程而不影响渲染进程。
- **安全性**：渲染进程加载的是宿主提供的本地内容，须按不可信内容对待。
- **i18n**：界面语言沿用 dsh 标准前端（本项目桌面壳文案为中文占位）。

## 5. 系统边界

**在范围内**：桌面壳装配、托盘、通知、无边框窗口、剪贴板（沿用 dsh）、生命周期、安全加固。

**不在范围内（暂缓）**：全局快捷键唤起、开机自启、多窗口。

**不做（沿用 dsh）**：原生文件/目录选择器（使用 dsh Web UI 内置目录浏览）。

**明确排除**：fork dsh UI、新写 IPC 数据载体、自定义协议加载、鉴权/CORS 注入（同源加载无需）。
